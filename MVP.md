# AM: спецификация MVP

## 1. Статус и назначение

Документ определяет предлагаемую границу первого полезного варианта AM на основе обсуждения продукта. Исходный локальный чат не публикуется; решения сохранены в документах репозитория. Полное направление развития находится в [PRODUCT.md](PRODUCT.md).

Поздние согласованные архитектурные решения находятся в [ARCHITECTURE.md](ARCHITECTURE.md), фактическое состояние и точка продолжения в [PLAN.md, раздел 13](PLAN.md#13-current-contract-and-agent-handoff). Контракт уточняет оставленные ниже вопросы формата компонентов, активации и полномочий, но не объявляет будущие механизмы реализованными и не включает весь harness в обязательный MVP.

Основные пользовательские решения зафиксированы. Детали, не выбранные в разговоре, обозначены как рекомендации или открытые вопросы. Требования приёмки ниже являются проектной формализацией этих потребностей, а не утверждением, что пользователь отдельно согласовал каждый тест, тип события или библиотеку.

MVP является универсальным агентом с делегированием, а не полноценной системой управления командой. В нём не обязательны доска задач, reviewer-workflow, веб, WASM или контейнеры. Однако их добавление не должно требовать переделки базового исполнения, полномочий и сохранения данных.

Примеры команд, конфигурации и состояний не фиксируют окончательный синтаксис.

## 2. Ценность первой версии

Пользователь может запустить агент локально, подключить выбранный совместимый API через нужный прокси, настроить shell и профиль, дать задание и понимать, что происходит.

Агент может исследовать и изменять проект, выполнять команды и делегировать независимую работу. Пользователь видит краткий статус команды, открывает разговор ребёнка и контролирует процессы, права и очередь.

При плохом результате ребёнка родитель читает сохранённые материалы. При прерывании или аварии сессия не исчезает, а неизвестные побочные эффекты не повторяются автоматически.

MVP должен быть удобен для обычного кодинга с 3-5 агентами. Архитектура и нагрузочные проверки учитывают сценарий 10-20 агентных состояний для CTF, не обещая одновременное тяжёлое исполнение каждого из них.

## 3. Граница объёма

### 3.1. Входит

| Область | Минимальный результат |
| --- | --- |
| Терминал | Ratatui, основной inline-режим, нативный scrollback и отдельные экраны подробностей |
| Состояние | Наблюдаемая фаза запроса/инструмента, длительность, последнее событие и явные ошибки |
| API | Произвольный endpoint выбранного совместимого протокола, streaming и tool calls |
| Прокси | SOCKS5, HTTP и HTTPS с тестируемой семантикой |
| Shell | Настраиваемый запуск и учёт управляемых команд |
| Файлы | Практически достаточные операции исследования и изменения проекта |
| Делегирование | Роли, дочерние агенты, свежий и постоянный контекст, ограниченная рекурсия |
| Модели | Модель и параметры по роли с разрешёнными переопределениями |
| Полномочия | Проверка вызовов, наследование ограничений, выдача прав и эскалация запросов |
| Ресурсы | Ограничение конкурентного исполнения, времени, вывода и явная матрица OS-лимитов |
| Материалы | История попытки, заметки и доступ к зарегистрированным результатам |
| Знания | Выбранные долговременные записи, ревью/редактирование и минимальный перенос |
| Хранение | Сохранение сессии, восстановление и раздельные квоты |
| Настройки | Файлы и runtime-управление с объяснением момента применения |
| Платформы | Linux/macOS с явно различающимися возможностями исполнения |

Это уже нетривиальный MVP. Уменьшать объём следует через исключение будущих слоёв и сложных режимов, а не через сокрытие отсутствующих гарантий.

### 3.2. Не входит как обязательное условие

- Доска долгоживущих задач, issue-комментарии и сложные назначения.
- Автоматические reviewer-переходы и bulletin board.
- Веб-клиент, HTTP-сервер управления и публикация в интернет.
- Многопользовательские аккаунты и разграничение между людьми.
- Полностью браузерный агент.
- WASM-runtime и стабильный публичный plugin SDK.
- MCP как обязательный способ реализации встроенных инструментов.
- Docker, Nix, Kubernetes или отдельный контейнер на каждого агента.
- Все аккаунтные способы входа, включая Codex-подобные интеграции.
- Строгая изоляция произвольного shell на всех платформах.
- Полная поддержка Windows и Termux.
- Векторная база и автоматическое превращение всей переписки в память.
- Неограниченная рекурсия и одинаковые hard-limit гарантии на всех ОС.

Автоматические суммаризаторы и агенты восстановления отчётов не вводятся. Это не просто необязательная функция: при плохом итоге ребёнка родитель читает материалы обычными инструментами, без отдельного автоматического шага оформления результата.

### 3.3. Что нельзя отложить вместе с расширением

Даже без веба нужны независимость runtime от конкретного экрана и структурированные события. Даже без sandbox нужны явные полномочия и честное описание гарантий. Даже без доски нужны идентификаторы агента, попытки и выполнения.

Это внутренние контракты, не требование сразу реализовать сервер, daemon или стабильный внешний API.

## 4. Терминальный контракт

### 4.1. Основной экран

Обычная работа не захватывает терминал постоянным fullscreen. В scrollback добавляется корневой разговор и ограниченный набор коротких событий прямых детей.

Живая область содержит ввод и технический статус. Уже опубликованная история не должна перерисовываться целиком при каждом токене.

```text
[root] Проверю тесты и распределю исследование.
[worker-1] started · parser
[worker-2] blocked · требуется действие

--------------------------------------------------------
root · API waiting for first event · 12s
team: 1 running · 1 blocked · processes: 1 · queued: 1
> _
```

Полная переписка детей сохраняется в хранилище, но не печатается в корневой терминальной истории автоматически.

### 4.2. Подробности

Временный отдельный экран позволяет:

- Просматривать сохранённую историю, включая историю длиннее terminal scrollback.
- Открывать разговор конкретного агента и писать ему.
- Видеть дерево участников и состояние их попыток.
- Просматривать процессы, заметки, материалы и запросы.
- Возвращаться к корневому inline-режиму без перепечатки дочернего чата.

Не требуется отдельная доска задач. Список участников с кратким текущим заданием и фактическим статусом достаточен.

Поиск по истории рекомендуется; конкретный объём поискового UI ещё не согласован.

### 4.3. Отзывчивость

Интерфейс должен оставаться управляемым при streaming, большом выводе команды и длинном журнале. Ввод не ждёт сетевой timeout и завершение процесса.

Рекомендация: рендерить только нужный диапазон истории, ограничивать буферы, объединять частые обновления и не выполнять блокирующие операции в UI-loop.

Численные цели задержки, размеры тестовой истории и эталонное железо необходимо определить до приёмки. Пока они не обсуждены, нельзя обещать конкретный FPS или время реакции.

### 4.4. Статус и анимации

Нужно различать подключение, ожидание ответа, получение streaming, исполнение инструмента, ожидание решения, ошибку сети и проблему хранения.

Показываются длительность фазы и последнее измеряемое событие. «Думает» не заменяет «ожидаем ответ», если сервер не сообщает reasoning-события. Недоступный показатель памяти не показывается как ноль.

Анимации допускаются, но не являются доказательством прогресса. Рекомендуется возможность отключения. Детальная диагностика открывается отдельно и не засоряет scrollback.

## 5. API и модельные настройки

### 5.1. Обязательные свойства

- Произвольный base URL или явно заданный адрес API без allowlist брендов.
- Непрозрачный model ID, без вывода capabilities из названия.
- Настраиваемая авторизация и headers с защитой секретов.
- Streaming текста и корректная сборка fragmented tool calls.
- Обработка обычного не-streaming результата в пределах выбранного адаптера.
- Понятные ошибки HTTP, TLS, формата ответа, context limit и неподдерживаемых параметров.
- Параметры совместимости, позволяющие не отправлять необязательные неподдерживаемые поля.
- Разделение провайдера, модели, credentials и runtime роли.

Поддержка файлов или изображений не была выбрана как обязательная часть MVP. Она не должна быть неявно обещана через слово «универсальный».

### 5.2. Протокол нужно выбрать явно

В разговоре не выбран начальный набор между Chat Completions и Responses. До реализации необходимо записать, какой протокол обязателен в MVP.

Рекомендация для сокращения объёма: начать с Chat Completions, сохранив границу для отдельного Responses-адаптера. Это предложение, не состоявшееся решение.

Если выбираются оба, их готовность проверяется отдельно. Произвольный совместимый endpoint не означает автоматическую поддержку обоих API.

### 5.3. Выбор по роли

Профиль может назначить сильную модель корневому агенту и дешёвую worker. Для участника доступны разрешённые переопределения.

Нельзя незаметно переключаться на другую модель или endpoint после ошибки. Такое поведение потребовало бы отдельной явно включённой политики.

Параметры reasoning и ограничения токенов являются свойствами конкретной модели/адаптера. Предупреждения о несовместимости должны быть понятными.

### 5.4. Авторизация

Конкретный минимальный набор auth-режимов нужно выбрать отдельно. Практическая рекомендация: отсутствие auth для локального сервера, bearer из разрешённого источника credentials и пользовательские headers.

Credentials не должны храниться как обычные сообщения, публиковаться в диагностике или автоматически наследоваться shell-окружением ребёнка. Будущий account login добавляется отдельно от агентного цикла.

## 6. Сетевой контракт

MVP проверяет не просто наличие поля proxy, а реальное прохождение запросов.

| Сценарий | Что требуется проверить |
| --- | --- |
| Прямой HTTP/HTTPS | Допустимая настройка, TLS и обработка отказов |
| HTTP destination через HTTP proxy | Правильный маршрут и auth прокси |
| HTTPS destination через HTTP proxy | CONNECT, затем TLS до origin, отсутствие plaintext origin traffic |
| HTTPS proxy | TLS до прокси и корректный транспорт до назначения |
| SOCKS5 | Auth и явно выбранное место DNS-resolution |
| Bypass | Объяснимое применение правил исключения |
| Обязательный proxy | Отказ без незаметного прямого соединения |
| Оборванный streaming | Частичный результат, ошибка и отсутствие повторного side effect |

Необходимо определить precedence конфигурации и proxy-переменных окружения. Рекомендация: явный режим, в котором среда не влияет на маршрут неожиданно.

Поддержка пользовательских CA рекомендуется для полного контроля TLS; способ настройки ещё не выбран. Отключение проверки сертификатов нельзя использовать как скрытое исправление проблем HTTPS-прокси.

Таймаут подключения и отсутствие событий streaming различаются. Активный долгий ответ не должен обрываться только из-за примитивного общего короткого timeout.

Повтор запроса ограничен и объясним. После неоднозначного результата не повторяются автоматически уже исполнявшиеся инструменты. Проксирование дочерних программ через environment является best effort, не гарантией сетевой изоляции.

## 7. Инструменты и исполнение

### 7.1. Минимальный набор

Рекомендуемый встроенный набор:

- Чтение файлов и просмотр каталогов.
- Поиск файлов и содержимого.
- Запись и редактирование с понятной областью действия.
- Выполнение shell-команд и управление длительными выполнениями.
- Создание и обслуживание разрешённых дочерних агентов.
- Доступ к материалам попыток и операции заметок.
- Доступ к разрешённым знаниям.
- Запросы недостающих данных и полномочий.

Окончательные имена и схемы инструментов не выбраны. Встроенный web fetch/search не был отдельно утверждён как условие MVP. Его наличие не заменяет сетевые возможности обычного shell.

### 7.2. Shell

Настраиваются executable, argv, cwd, environment, startup-поведение, таймаут и режим вывода. Не нужен ограниченный список «правильных» оболочек, если исполнитель умеет запустить заданный executable; семантика аргументов остаётся ответственностью выбранного профиля.

Captured-выполнение с управляемым выводом является рекомендуемой базой. Persistent shell и интерактивный PTY не включаются автоматически в обязательный объём. Их следует выбрать отдельно.

Нельзя подменять выбранный shell другим без объяснения. Ошибка настройки должна быть диагностируема до первого неожиданного действия.

### 7.3. Управляемый процесс

У каждого выполнения есть ID, владелец, попытка, параметры запуска, состояние и результат. Длительное выполнение возвращает ссылку для дальнейшего чтения статуса/вывода и остановки.

Команды не должны требовать запуска через неучтённый `&`, чтобы пережить длительный вызов. При этом поведение произвольного shell, самостоятельно daemonizing-потомков и фоновых серверов должно быть описано отдельно.

Вывод читается с bounded memory. UI и модель получают ограниченное представление; полный материал сохраняется только в пределах квот. При усечении это явно обозначается.

Escape-последовательности вывода не управляют терминальным UI. Исходный материал и безопасная проекция различаются.

### 7.4. Завершение

Рекомендация: отмена передаётся через все обёртки, затем выполняется graceful-stop с дедлайном, escalation при необходимости и reap управляемого процесса.

Задачу нельзя объявить полностью остановленной, пока подтверждён только запрос отмены. Оставшиеся или недоступные наблюдению процессы обозначаются явно.

Строгое уничтожение всех произвольно отделившихся потомков не обещается обычным process group. Возможность определяется исполнителем.

## 8. Роли, контекст и делегирование

Корневой агент и ребёнок используют один механизм. Различия находятся в эффективных настройках и полномочиях.

При создании ребёнка задаются роль, сообщение-задание, режим контекста, выбранные материалы и допустимые переопределения. Runtime проверяет это до запуска.

Свежая попытка не наследует переписку родителя или прежнего worker. Постоянный участник может получать следующие задания с сохранённым контекстом.

Доступ к заметкам не вставляет их автоматически в prompt. Ребёнок читает выбранные материалы по необходимости, а недостающие данные может запросить вверх при наличии права.

Нужны ограничения глубины, числа участников и суммарной активности ветки. Конкретные числа не выбираются по примеру kraber и не фиксируются этим документом.

Бюджет не умножается при spawn. Ожидающий ребёнок не должен бесконечно опрашивать родителя запросами модели.

Профиль роли и существующий участник различаются. Изменение профиля не обновляет работающую команду молча.

## 9. Полномочия и запросы

### 9.1. Проверка

Каждый вызов авторизуется runtime с доверенной идентичностью инициатора. Нельзя принимать agent ID и роль из произвольных аргументов модели как доказательство права.

Проверяются применимые настройки хоста, цепочки делегирования, участника, материала и исполнителя. Скрытие инструмента из списка модели не является единственной защитой.

Создание ребёнка, смена модели, изменение профиля и предоставление доступа также являются проверяемыми действиями, а не административными обходами.

### 9.2. Разрешение родителем

Родитель может одобрить расширение в пределах своей делегируемой власти. Остальное отклоняет либо передаёт выше, если такая передача разрешена.

Hard host limits изменяет только оператор. Full access не отменяет это правило. Для конкретных категорий можно запретить даже запрос на расширение.

Одобрение конкретной shell-команды обсуждалось, но язык правил и достаточные условия одобрения ещё не определены. Ни один профиль не должен обещать read-only безопасность при фактически unrestricted shell.

### 9.3. Работа без оператора

Раздельно управляются запрос, уведомление и запись препятствия. При запрещённых вопросах попытка может ждать или продолжать разрешённую работу, сохраняя причину блокировки.

На главном экране доступно число пунктов, требующих действия. Независимые участники продолжают работу.

Рекомендуются ограничение pending-запросов, дедупликация и представление пакетом. Точные правила timeout и повторов остаются открытыми.

## 10. Очередь и остановка

### 10.1. Сообщения

Сообщение можно отправить во время выполнения, увидеть в очереди, отменить до принятия и отредактировать.

Редактируемый текст не обрабатывается автоматически. Переход queued-сообщения в editing согласуется с runtime. Если сообщение уже принято, это показывается явно.

Сообщение привязано к адресату. Переключение экрана не перенаправляет его.

Необходимо определить безопасную точку приёма очереди. В разговоре обсуждалась обработка после завершения/прерывания генерации; mid-turn steering не считается утверждённым требованием.

### 10.2. Остановка

Esc является обычным способом прерывания без закрытия сессии. Первый Ctrl+C требует подтверждения, а не мгновенного завершения.

Есть отдельная операция полной остановки выбранного агента и его ветки. Рекомендуется использовать дерево владения, не произвольные зависимости задач.

Перед реализацией нужно определить действие Esc на активный инструмент, судьбу queued-сообщений, повторный Ctrl+C и закреплённые процессы. Ни один из вариантов не должен выдавать остановку за откат уже выполненных side effects.

## 11. Ограничения ресурсов

### 11.1. Уровень runtime

Минимально необходимы проверяемые лимиты числа агентов, глубины, активных запросов, конкурентных команд, wall time и размера вывода. Они могут работать без отдельного контейнерного backend.

Количество управляемых выполнений и число OS-процессов различаются. Лимит первого нельзя показывать как строгий лимит второго.

### 11.2. Уровень ОС

Память, CPU и число процессов должны быть представлены в конфигурации и capabilities исполнителя. Реальные гарантии проверяются по платформам.

Возможный путь Linux: cgroups v2 при доступных правах. Для macOS необходимо отдельно определить поддерживаемые пределы. Обычный per-process rlimit нельзя обозначать как эквивалент совокупного лимита всей ветки.

Строгий требуемый лимит либо исполняется, либо запуск отклоняется. Более слабый режим допускается только как явно выбранная политика, не автоматическое fallback.

MVP не обязан иметь sandbox backend на всех ОС, но обязан честно показывать отсутствие гарантий и не игнорировать выбранное strict-требование.

### 11.3. Пресеты

Нужны настраиваемые окружения для общего каталога и независимой работы. Git worktree и сложные sandbox-пресеты могут добавляться позже, если базовый интерфейс рабочего окружения сохранён.

Пресет не создаёт новую копию всех лимитов детям. Распределение бюджета обязано сохранять общий предел ветки.

## 12. Материалы, заметки и знания

### 12.1. След попытки

Сохраняются сообщения, результаты вызовов, техническое завершение и ссылки на зарегистрированные материалы. Агент может писать заметки отдельным инструментом.

Родитель должен иметь предусмотренный политикой способ прочитать материалы ребёнка. Практическая рекомендация: обычный профиль делегирования даёт доступ к своей попытке без отдельного вопроса на каждую заметку.

Если ребёнок не выдал хороший итог, родитель просто читает имеющиеся материалы. Автоматический summarization/rescue шаг, дополнительный worker или скрытый API-вызов ради оформления отчёта не запускаются. Это не запрещает обычную работу родителя с моделью или явно разрешённое делегирование другого задания.

Нельзя автоматически считать задачу решённой только по техническому завершению попытки. При этом сложный semantic-validator отчётов не нужен.

### 12.2. Заметки

Нужны создание, чтение, перечисление и разрешённое редактирование/удаление заметок с привязкой к попытке. Желательны тип и источник, но конкретная схема не выбрана.

Содержание заметок не распространяется всем участникам и не включается в prompt без выбора. Доступ к заметке не даёт право расширять её аудиторию.

### 12.3. Знания

В MVP предлагается минимальная возможность сохранить выбранный материал за пределами сессии, прочитать его, проверить и исправить оператором, а также перенести на другой хост.

Знания проекта меняются согласно правам. Изменение глобальных знаний контролирует оператор. Не требуется отдельное согласование каждой уже разрешённой проектной правки.

Рекомендация: читаемые записи с метаданными и источником, плюс простая упаковка выбранных записей. ZIP/TAR, manifest и конкретный формат не выбраны. Векторный индекс и автоматическое извлечение всей памяти не нужны.

Импорт не исполняет содержимое, не применяет чужие права автоматически и не меняет роли. Сжатие не должно скрыто суммаризировать текст моделью.

## 13. Хранение и восстановление

### 13.1. Категории и квоты

Разделяются заметки, знания, чаты, журнал восстановления, артефакты и диагностика. Для заметок и истории нужны раздельные настраиваемые пределы. У артефактов и диагностики рекомендуется собственный учёт.

Ротация технических логов не должна удалять заметки или нарушать восстановление. Исключение материала из доступного контекста не равно физическому удалению.

Поведение при quota/full disk необходимо определить и протестировать. Нельзя подтвердить сохранение потерянной записи или продолжать бесконтрольно буферизовать данные в памяти.

Рекомендуется резерв под журнал восстановления и остановка новых изменяющих действий при невозможности их надёжного учёта.

### 13.2. Durability

Состояние записывается во время работы, не только при выходе. Принятая очередь, значимые переходы исполнения и разрешения должны иметь определённые гарантии сохранения.

После аварии интерфейс показывает последнее сохранённое состояние и неоднозначные действия. Неизвестный результат не вызывает автоматического повторного исполнения.

Процесс нельзя «продолжить» после отключения питания. После падения runtime surviving-процессы требуют проверки. Полноценный attach к пережившему процессу не обязателен в MVP, но ложный статус завершения недопустим.

### 13.3. Формат

Поздний PLAN выбрал SQLite/WAL/FULL для состояния и отдельные файлы артефактов; это реализовано в offline-ядре, но не подтверждает готовность всего MVP. Формат долговременных знаний и их переноса определяется отдельно.

До реализации выбираются формат, транзакционность, fsync-политика, допустимое окно потери и способ проверки согласованности. Число токенов, потерянных при аварии, не должно быть скрытой неопределённостью продукта.

## 14. Конфигурация и runtime-изменения

Файлы позволяют создавать роли массово и переносить настройки. Интерфейс позволяет менять допустимые параметры хоста, сессии и конкретного агента.

Для значения показываются эффективный результат, источник и момент применения. Изменение шаблона не должно молча менять действующий экземпляр.

Категории применения: сразу, на следующей безопасной границе, для новых исполнений/участников или после рестарта. Точный перечень по полям нужно определить.

Доступ к изменению конфигурации также проверяется. Нельзя через настройку вызвать действие, запрещённое обычному инструменту. Hard host limits и глобальные знания остаются под операторским контролем.

Поздний архитектурный контракт выбрал TOML/Markdown, явную композицию компонентов и пространства имён без молчаливой подмены, фиксированные версии экземпляров и проверяемую активацию. Конкретная семантика overrides задаётся по полям, а не универсальным deep merge. Недоверенный проектный файл не может самовольно расширять права или читать credentials; действующие права проверяются независимо от сохранённого снимка конфигурации.

## 15. Минимальные внутренние интерфейсы

| Граница | Что необходимо сохранить для будущего |
| --- | --- |
| Провайдер | Нормализованные текст, tool calls, завершение, ошибки и transport-статус |
| Credentials | Авторизация без привязки к терминальному UI |
| Инструмент | Проверяемый вызов с доверенным контекстом и структурированным результатом |
| Исполнитель | ID, владелец, capabilities, запуск, чтение состояния, отмена и завершение |
| Управление runtime | Команды, снимок состояния, агентные идентификаторы и события |
| Хранилище | Сессии, попытки, очередь, материалы, версии и восстановление |

Рекомендуется возможность читать события после курсора и различать command ID, request ID и execution ID там, где это предотвращает повторы. Это не требует реализации веб-протокола сейчас.

Интерфейсы остаются внутренними. Не требуется стабильный SDK, отдельный сервис на каждую границу или будущая доска в виде неработающих заглушек.

Архитектурный тест будущего расширения: доска назначает работу существующим агентам и наблюдает существующие попытки; веб вызывает те же операции, что терминал; новый executor сохраняет общие полномочия и владение.

## 16. Платформенная граница

Linux и macOS являются начальными платформами. Матрица возможностей должна различать терминал, shell, остановку и OS-лимиты.

Пути, расположение данных, executable и сигналы не должны быть безусловно Unix-хардкодом в общем ядре. Termux и Windows учитываются как будущие targets, но не заявляются поддержанными без проверки.

Rust является рекомендуемым выбором для ratatui-направления. Конкретные async, HTTP, TLS и storage-библиотеки ещё не выбраны. Отсутствие Docker/Nix в минимальном сценарии не означает обещание полностью статического бинарника без системных зависимостей.

## 17. Пользовательские сценарии приёмки

### 17.1. Одиночная работа

Пользователь задаёт endpoint, credentials, model и shell, запускает задание, получает streaming, видит команду и результат. Может прокрутить нативную историю, открыть сохранённый журнал и вернуться без потери ввода.

### 17.2. Разные модели в команде

Корневой агент использует модель A, worker модель B. Ребёнок получает задание и доступ к выбранной заметке, но не родительский разговор. Модель и параметры каждого запроса соответствуют настройкам его участника.

### 17.3. Свежая попытка

После неудачного подхода запускается другая попытка того же профиля. Старые рассуждения не попадают в новый запрос без явного выбора. Старые материалы остаются доступными авторизованному родителю.

### 17.4. Плохой итог ребёнка

Ребёнок завершается с коротким или бесполезным сообщением. Родитель видит сохранённые вызовы, заметки и зарегистрированные артефакты и читает нужное. Runtime не запускает summarizer или дополнительный API-запрос ради отчёта.

### 17.5. Ограниченное unattended-исполнение

Расширение прав запрещено, а часть работы требует недоступного действия. Агент не обходит запрет через ребёнка. Может ожидать с видимой причиной; независимая работа продолжается. Оператор не получает бесконечную очередь одинаковых вопросов.

### 17.6. Остановка ветки

Выбрана ветка с ребёнком и активными командами. Full stop прекращает её дальнейшую работу и обрабатывает принадлежащее исполнение. Соседняя ветка продолжает. Не подтверждённое завершение не показывается как успешная остановка.

### 17.7. Очередь во время работы

Пользователь отправляет сообщение, начинает редактирование и продолжает печатать. Агент не забирает редактируемый текст. При уже принятом сообщении интерфейс сообщает об этом. Отмена queued-сообщения не превращается в отправку.

### 17.8. Сбой и восстановление

Runtime прерывается между началом инструмента и записью результата. После запуска сохранённая сессия доступна, а выполнение помечено для проверки. Изменяющая команда не повторяется сама.

### 17.9. Перенос знаний

Оператор выбирает записи, проверяет и исправляет их, переносит пакет на другой хост. Текст и источник сохранены. Доступ задаётся для нового окружения; импорт не расширяет права и не исполняет инструкции.

## 19. Решения до начала реализации соответствующих частей

| Решение | Почему необходимо |
| --- | --- |
| Начальный API-протокол и capabilities | Определяет формат streaming, историю и tool calls |
| Стек языка/async/HTTP/TLS | Ratatui не определяет транспорт и исполнение |
| Формат config и precedence | Нельзя реализовать «полный контроль» с неоднозначным наследованием |
| Auth и источники credentials | Влияют на секреты, окружение и будущий login |
| Esc, Ctrl+C, очередь и stop-tree | Предотвращает противоречивое управление |
| Контекст при переполнении | Нельзя скрыто суммаризировать или обрезать важные данные |
| Минимум shell/PTY/persistent mode | Существенно меняет сложность supervisor |
| Матрица OS-limits | Определяет честные профили Linux/macOS |
| Default ACL материалов | Связывает доступ родителя и выбранный доступ детей |
| Хранилище и durability | Определяет окно потери и восстановление |
| Квоты и retention | Определяет поведение при заполнении диска |
| Формат знания и перенос | Требуется проверяемый результат без непрозрачной базы |
| Порог отзывчивости и тестовое железо | Делает критерий качества измеримым |

Эти вопросы не означают, что весь продукт нужно переобсудить. Они фиксируют места, где обсуждение задало цель, но ещё не выбрало механизм.

## 20. Итоговый критерий MVP

Первый вариант готов, когда можно безопасно в смысле выданных и честно описанных полномочий выполнить одиночную и делегированную работу, видеть реальное состояние, управлять очередью и процессами, сохранять материалы и продолжать взаимодействие после прерывания или аварии.

Наличие большого числа инструментов, анимаций или ролей не компенсирует непроверенный HTTPS proxy, потерю отмены, бесконтрольный вывод, неясное состояние или повторное исполнение команды после сбоя.

MVP не обещает sandbox там, где его нет, и не требует полного harness. Он создаёт управляемую основу, на которую будущая доска, workflow, авторизация и веб добавляются без второго ядра.
